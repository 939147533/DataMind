# 一、AI Agent · 方言与上下文隔离

## A1 会话内切换数据源时，历史 SQL 未按数据源隔离

**级别**：P1

**位置**
- `backend/app/services/agent_service.py:130-143`（`_load_history`）
- `backend/app/services/agent_service.py:318-322`（`agent_chat` 数据源解析）

**现状**

`_load_history` 只按 `session_id` 取最近 10 条 `text` / `sql` 消息，**不区分数据源**：

```python
.where(AgentMessage.session_id == session_id, AgentMessage.role.in_(["user", "assistant"]))
```

而 `datasource_id` 是**每次请求**由前端传入的（`frontend/src/stores/agent.ts:101`），可以与会话创建时的数据源不同。

**影响**

在 MySQL 数据源下聊几轮后切到 Oracle 继续追问，前几轮的 MySQL 方言 SQL 仍留在上下文里，模型可能沿用错误方言 —— 例如继续生成 `LIMIT N`，而 Oracle 需要 `FETCH FIRST N ROWS ONLY`。

**建议方案（三选一，按改动成本排序）**

1. **零改动**：前端切换数据源时提示「数据源已变更，建议新建对话」，或直接自动新建会话。改动最小、无迁移风险，体验略生硬。
2. **上下文截断**：`agent_chat` 里检测到 `datasource_id != session.datasource_id` 时，`_load_history` 只取该切换点之后的消息（需要一条标记消息或按 `updated_at` 截断）。无需数据库迁移。
3. **彻底方案**：给 `agent_messages` 表加 `datasource_id` 列（`models.py:98-105` 加字段 + Alembic 迁移），`_load_history` 增加 `where(AgentMessage.datasource_id == 当前 ds)`。最干净，但要动表结构。

**验证方式**：建会话选 MySQL → 问 2 轮 → 切到 Oracle → 追问同类问题，检查生成的 SQL 是否仍带 MySQL 方言。

**状态**：✅ 已修复（2026-10-20）

**修复说明**：采用方案 2 的「标记消息」变体（**无需数据库迁移**，老库直接可用）——`agent_messages` 增加一种 `message_type="ds_switch"` 的边界标记行，切换数据源时写入，`_load_history` 只取最后一条标记之后的消息。选它而不是方案 3（加 `datasource_id` 列）的原因：`create_all` 不会给已有表加列，加列必须配 Alembic 迁移，否则现有 `app.db` 会直接报「no such column」。
- `agent_service.py`：新增 `DS_SWITCH_TYPE` / `_last_switch_id()` / `switch_session_datasource()`；`_load_history` 增加 `AgentMessage.id > since` 过滤；`list_messages` 过滤标记行（前端不会看到）；
- `agent_chat` 检测到传入的数据源与会话记录不一致时自动打标记（A4 的服务端兜底）。

## A2 Schema / 方言获取失败时静默降级

**级别**：P1

**位置**：`backend/app/services/agent_service.py:159-160`

**现状**

```python
except Exception:  # noqa: BLE001
    return {"schema": "（Schema 获取失败）", "db_type": db_type, "dialect_hint": ""}
```

任何异常（数据库连不上、驱动缺失、SSH 隧道建立失败）都被吞掉，`dialect_hint` 退化为空串。

**影响**

模型同时失去表结构摘要和方言约束，却仍会照常生成 SQL。用户看到的只是「结果不对」，界面上没有任何提示说明方言约束已丢失，排查困难。

**建议方案**

1. **保留降级行为**（不要因为 Schema 拉取失败就让整个请求失败），但把失败透出去：
   - SSE 流增加 `warning` 事件，前端在消息气泡上方显示浅色提示条；
   - 同时写入 `audit_logs`（状态 `failed`），便于事后统计失败率。
2. 补 `logger.warning(...)`，至少能在服务端日志里定位。
3. 可选：降级时在 `SYSTEM_TEMPLATE` 里追加一句「未能获取表结构，请勿臆测表名列名，必要时先调用工具确认」。

**状态**：✅ 已修复（2026-10-20）

**修复说明**：保留降级行为（不因元数据拉取失败就让整个提问失败），但把失败透出去：
- `_schema_info()` 增加 `warning` 字段，`except` 分支记 `logger.warning`（带数据源 id / db_type / 异常）；
- `agent_chat` 收到 warning 时先发一个 SSE `warning` 事件；
- 前端 `stores/agent.ts` 新增 `warning` 事件分支，`SmartQueryView` 用 `n-alert` 浅色提示条展示。

> 与清单原建议的差异：**没有**写 `audit_logs`。原因是审计按 `(action_type, status)` 统计，混进 `agent_action/failed` 会污染既有的失败率基线；服务端日志 + 前端提示已满足「可定位」的目标。若后续需要统计 Schema 失败率，建议单独开 `action_type="agent_schema"`。

## A3 MongoDB 适配器缺少 dialect_hint

**级别**：P2

**位置**：`backend/app/adapters/mongodb_adapter.py`、`backend/app/adapters/base.py:73`

**现状**

`BaseDBAdapter.dialect_hint = ""`，`MongoDBAdapter` 未覆写，因此 `SYSTEM_TEMPLATE` 里 `{dialect_hint}` 那一行是空行。

对比：MySQL / PostgreSQL / Oracle / SQLite 四个适配器都定义了具体的 `dialect_hint`。

**影响**

MongoDB 不走 SQL，但 Agent 仍被要求输出 SQL。缺少提示时模型容易生成关系型写法。当前影响有限，但属于明确的能力缺口。

**建议方案**

- 给 `MongoDBAdapter` 补 `dialect_hint`，说明「当前数据源为 MongoDB，不支持 SQL」；
- 或更彻底：在 `_schema_info` 里对 MongoDB 走独立分支，让 Agent 只用 `answer` 字段回复、不生成 SQL。

**状态**：✅ 已修复（2026-10-20）

**修复说明**：采用「补 dialect_hint」这一档（改动最小、不动 Agent 主链路）：`MongoDBAdapter.dialect_hint` 明确说明当前数据源为 MongoDB、不支持 SQL，并引导模型改用 `list_tables / get_columns / sample_data` 工具 + `answer` 字段作答。

## A4 session.datasource_id 与实际选择不一致

**级别**：P2

**位置**：`frontend/src/views/SmartQueryView.vue:275-279`、`backend/app/services/agent_service.py:318-319`

**现状**

```js
watch(dsId, (v) => {
  agent.datasourceId = v;
  if (v) localStorage.setItem("agent.datasourceId", String(v));
  else localStorage.removeItem("agent.datasourceId");
});
```

只更新了 Pinia store 和 localStorage，**没有回写会话记录**。后端 `session.datasource_id` 仍是建会话时的值。

**影响**

- 「会话记录里的数据源」与「实际在用的数据源」不一致，排查问题时容易误判；
- `agent_chat` 的兜底分支 `if datasource_id is None: datasource_id = session.datasource_id` 会退回到过期值。

**建议方案**

- 在切换时调用 `PATCH /api/agent/sessions/{id}` 更新 `session.datasource_id`；或
- 明确约定「会话数据源不可变」，切换即新建会话（可与 A1 方案 1 合并处理）。

**状态**：✅ 已修复（2026-10-20）

**修复说明**：走「调用 PATCH 回写」这条路，双向都同步：
- 后端新增 `PATCH /api/agent/sessions/{id}`（`routers/agent.py`）→ `agent_service.switch_session_datasource()`，改会话数据源的同时落 A1 的边界标记；
- 前端 `SmartQueryView` 的 `watch(dsId)` 在切换时调用该接口；从历史会话列表切回来时，数据源跟回会话记录的值，避免「记录里是 Oracle、实际在查 MySQL」；
- `agent_chat` 里保留兜底：若前端没同步成功，服务端仍按实际传入的数据源纠正并打标记。

## A5 MySQL 按小写键取 information_schema 的大写列名，Schema 摘要必然失败

**级别**：P1

**位置**：`backend/app/adapters/mysql_adapter.py:80-92`（列查询）、`:105-116`（索引查询）、`backend/app/adapters/base.py:204-225`（摘要范围）

**现象**

MySQL 数据源下每次 AI 提问都会提示：

> mysql 未能获取表结构与方言提示（'numeric_precision'），本次回答可能不准确；请确认数据源可连通后重试。

**根因**

pymysql 的 `DictCursor` 用**服务端返回的字段名**做键，而 MySQL / OceanBase 的 `information_schema` 列名是大写的。查询里除 `numeric_precision` / `numeric_scale` 外都起了别名：

```sql
SELECT column_name AS name, data_type AS data_type,
       character_maximum_length AS char_length, numeric_precision, numeric_scale, ...
```

所以只有这两列以 `NUMERIC_PRECISION` / `NUMERIC_SCALE` 返回，`r["numeric_precision"]` 直接 `KeyError`。同一个坑还有 `get_table_indexes` 的 `non_unique` / `column_name` / `index_type`。

**影响**

- `get_table_columns` 抛异常 → `schema_summary()` 整体失败 → 模型既没有表结构也没有方言提示，生成的 SQL 只能靠猜；
- 对象树的「列详情」同样调 `get_table_columns`，MySQL 下也会失败；
- `get_table_indexes` 是潜在同类故障，只是摘要链路先崩，没走到它。

**修复**

- `mysql_adapter.py` 新增 `_Row`（大小写无关的 dict 子类），`_query()` 统一返回 `_Row`：保留原始键（`SELECT *` 的列名要原样展示），查找时忽略大小写 —— 一处修复覆盖当前与将来所有未起别名的 I_S 列；
- `base.py` 抽出 `summary_schemas()` 钩子，`schema_summary()` 改用它；
- `mysql_adapter.summary_schemas()`：优先只用 `database_name`，否则过滤 `information_schema` / `mysql` / `performance_schema` / `sys` / `oceanbase`。**否则即便 KeyError 修好，摘要也会被系统库按字母序挤满**（`information_schema` 排最前）；
- `mongodb_adapter.summary_schemas()`：`get_tables` 忽略 schema 参数、始终用当前库，原实现会把同一份摘要重复 5 遍。

**状态**：✅ 已修复（2026-10-23）

**回归测试**：`tests/test_hardening.py` 新增 3 条 —— `test_mysql_columns_tolerate_uppercase_information_schema_keys`、`test_mysql_indexes_tolerate_uppercase_information_schema_keys`、`test_mysql_summary_schemas_prefers_connected_database`。

## D1 check_sql_permission 在 user_id 为空时直接放行（fail-open）

**级别**：P1

**位置**
- `backend/app/permissions.py:112-114`（`check_sql_permission` 定义）
- 受影响调用点：`backend/app/services/sql_service.py:518`（首次执行）、`sql_service.py:569`（确认后执行）

**现状**

```python
async def check_sql_permission(db: AsyncSession, user_id, op_type: str) -> None:
    if not user_id:
        return          # ← user_id 为 None / 0 时直接返回，不做任何鉴权
    user = (await db.execute(select(User).where(User.id == user_id))).scalar_one_or_none()
    ...
```

`user_id` 为空（`None` / `0`）时函数**直接返回** —— 既不查用户、也不校验权限。这是典型的 **fail-open（默认放行）** 写法。

**影响**

当前**不可达**。已逐一核实所有调用点都传了真实的 `user.id`：

| 调用点 | 传参 |
|---|---|
| `routers/sql.py:20` | `user.id` |
| `routers/metadata.py:116`（`alter_table`） | `user.id` |
| `routers/metadata.py:64 / 75 / 86`（行编辑，经 `metadata_service.py:175 / 183 / 191`） | `user.id` |
| `routers/agent.py:61` → `agent_service.py:422 / 518` | `user.id` |

但这条路径**只差一步就会真实可达**，有两个明确诱因：

1. `execute_sql` 的签名本身就是 `user_id: int | None`（`sql_service.py:511`），类型上明确允许 None；
2. `pending_executions.user_id` 是**可空列**（`models.py:130`，`nullable=True`），而确认执行时读的是 `entry.get("user_id")`（`sql_service.py:569`）。

也就是说：**只要将来任何一个 `execute_sql` 调用点漏传 `user_id`，写操作会先落一条 `user_id=NULL` 的待确认记录；用户点击确认后，`confirm_execution` 走到 `check_sql_permission(db, None, "DDL")` 便直接放行 —— DDL/DML 在完全不做权限校验的情况下执行，既不报错、也不会留下 `denied` 审计。**

**建议方案**

1. **改成 fail-closed（推荐）**：`user_id` 为空时抛 401，让漏传立刻暴露，而不是静默越权：

```python
if not user_id:
    raise HTTPException(status_code=401, detail="未认证")
```

2. **收紧类型**：把 `execute_sql` 的 `user_id` 由 `int | None` 改为必填 `int`；`metadata_service` 的三个行编辑函数同理，去掉 `user_id: int | None = None` 的默认值。这样漏传会在调用处就报错。

3. **补一条回归测试**：在 `tests/` 新增用例，直接调用 `check_sql_permission(db, None, "DDL")` 并断言抛 401，锁住行为。

**验证方式**

```bash
cd backend
grep -rn "check_sql_permission" app/          # 确认只有 permissions.py 定义 + sql_service.py 两处调用
python -c "import asyncio; from app.permissions import check_sql_permission; asyncio.run(check_sql_permission(None, None, 'DDL'))"   # 期望抛 401，而非静默通过
```

**状态**：✅ 已修复（2026-10-20）

**修复说明**：按建议方案 1+2+3 全部落地：
1. `permissions.check_sql_permission` 改为 **fail-closed**：`user_id` 为空直接 `raise HTTPException(401, "未认证：缺少执行该操作的用户身份")`；
2. 收紧类型：`execute_sql(user_id: int)`、`_create_execution(user_id: int)`、`metadata_service.update/insert/delete_table_row(user_id: int)`，去掉 `int | None` 与默认值 —— 漏传会在调用处就暴露；
3. 补回归测试 `tests/test_hardening.py::test_check_sql_permission_rejects_missing_user`（READ/DML/DDL 三档均断言 401）。

> 兼容性确认：`pending_executions` 当前 0 条记录，且已核实所有调用点都传 `user.id`，改为 fail-closed 不会打断既有流程。

## D2 decrypt_text 静默吞掉异常，解密失败伪装成空值

**级别**：P2

**位置**：`backend/app/security.py:73-79`

**现状**

```python
def decrypt_text(token: str | None) -> str:
    if not token:
        return ""
    try:
        return _get_fernet().decrypt(token.encode("utf-8")).decode("utf-8")
    except Exception:
        return ""
```

任何解密失败 —— 密钥被换、token 被截断、字段格式非法、密钥文件损坏 —— 都返回空字符串，**不区分「本来就是空」与「解密失败」**，也不记日志。

**影响**

已核实的调用点共 4 处：

| 调用点 | 用途 | 解密失败时的表现 |
|---|---|---|
| `services/sql_service.py:295` | 取数据源密码去连库 | 用空密码连库 → 报「Access denied for user」 |
| `services/sql_service.py:302` | 取 SSH 私钥 | 隧道认证失败 → 报 SSH 认证错误 |
| `services/llm_providers.py:22` | 取大模型 API Key | 报「API Key 无效 / 401」 |
| `routers/system.py:55` | 测试连接时取已存 Key | 测试结果报 Key 无效 |

四个场景都会把**「密钥问题」伪装成「凭据问题」**，排查时容易在错误的方向上绕远路。

另外 `_ai_out()`（`routers/system.py:21-31`）对外只暴露 `has_key: bool(c.api_key)` —— 它判断的是「密文串非空」，不是「能解密」。密钥丢失后界面仍显示「已配置 Key」，与实际的不可用状态矛盾。

**已排除的风险（重要）**

确认**不存在「解密失败 → 空值被回写覆盖」的数据丢失路径**：

- `connection_service.update_connection`（`connection_service.py:99-102`）有 `if data.password:` / `if data.ssh_private_key:` 守卫，空值不会覆盖原密文；

## D3 Cookie 缺 secure 属性、登录响应体多余回传 session token

**级别**：P2（安全加固；当前不影响功能）

**位置**：`backend/app/routers/auth.py:59-60`

**现状**

```python
response = JSONResponse(content=ok({"token": token, "user": _user_dict(user, sorted(perms))}, "登录成功"))
response.set_cookie(SESSION_COOKIE, token, httponly=True, max_age=SESSION_TTL_SECONDS, samesite="lax")
```

两个问题：

1. **`set_cookie` 未设 `secure=True`** —— cookie 在 HTTP 明文连接下也会被发送；
2. **响应体把同一个 `token` 又放回 JSON** —— 前端全程用 `credentials: "include"` 依赖 cookie（见 `frontend/src/api/*`），并未读取该字段；token 一旦进入 JS 可读的响应体，`HttpOnly` 的保护就形同虚设（XSS 或任何记录响应体的中间层都能拿到会话）。

**影响**

- 第 1 条**不能无条件加 `secure=True`**：当前单端口 8000 部署多为 HTTP，加了会导致 HTTP 下 cookie 不发送、直接登录失败。必须按环境区分。
- 第 2 条是纯粹的暴露面扩大，删掉即可，无兼容风险。

**建议方案**

1. 响应体移除 `token`，只保留 `user`；先核实前端未读取（见验证方式）。
2. `secure` 按环境配置：在 `config.py` 增加 `COOKIE_SECURE`（默认 `False`，生产环境设 `True`），改为 `set_cookie(..., secure=COOKIE_SECURE)`。
3. `HttpOnly` / `SameSite=Lax` 已具备，保持即可。

**验证方式**

```bash

grep -rn "credentials" frontend/src/api/                       # 确认全部 include
grep -rn "\.token" frontend/src/stores/auth.ts                 # 确认前端未读取登录返回的 token
```

**状态**：✅ 已修复（2026-10-20）

**修复说明**：
1. 登录响应体只返回 `{"user": ...}`，**不再回传 token**（已核实前端 `stores/auth.ts` 只用 `data.user`，`http` 封装全程 `credentials: "include"`）；

**位置**

1. **统一入口**：把 `agent_service._record_audit`、`users._log`、`roles` / `auth` 的直接构造改为调用 `audit_service.record_audit`；`sql_service._record_audit` 已是薄包装，可保留也可直接删除。
2. **明确失败策略**（需产品 / 合规确认，二选一）：

3. 若选「审计优先」，建议把审计写入与业务写入放进**同一事务**（当前是两次独立 `commit`），语义更清晰。

```python
chart = _parse_chart(parsed.get("chart"))
```

**影响**

用户提问「按月份统计订单并画个图」→ 模型首轮 SQL 有笔误（列名写错等）→ 触发自动修正 → 修正成功、结果正常返回，**但修正后的 JSON 未带 `chart`，图表消失**。前端 `SmartQueryView.vue:40-43` 仅在 `item.chart` 存在时渲染 `ChartCard`，因此表现为「只有表格、没有图」，且**没有任何提示**，用户只会以为「这次没出图」。

SQL 越容易出错（复杂多表、方言差异大）的场景，越容易踩到。

**建议方案（按推荐度排序）**

1. **把图表解析提前**（最稳）：在修正循环**之前**就从首轮 `parsed` 解析出 `chart` 并保存到局部变量，修正循环只更新 `sql`。图表配置与 SQL 文本本就解耦，无需被修正流程牵连。
2. **备份 + 回填**：循环前 `original_chart = parsed.get("chart")`，`:468` 处若 `parsed.get("chart")` 为空则回填 `original_chart`。改动最小。
3. **补提示语**：在修正提示语末尾加「并保留原有的 chart 配置字段」。依赖模型配合，可靠性最低，建议与方案 1 或 2 并用。

**验证方式**

构造首轮必然报错的提问（如引导模型引用不存在的列名），确认修正成功后图表是否仍然出现：

```bash

grep -n "parsed = _extract_json" app/services/agent_service.py   # 定位覆盖点（当前为 :440）
grep -n "chart = _parse_chart" app/services/agent_service.py     # 定位解析点（当前为 :468）
```

**状态**：✅ 已修复（2026-10-20）

**修复说明**：采用建议方案 1（**把图表解析提前**）：`_parse_chart(parsed.get("chart"))` 移到 READ 分支的修正循环**之前**，修正循环只更新 `sql`，不再能覆盖图表配置。另加一道保护 `_chart_fits_columns()`：修正后的 SQL 若换了列名，图表引用的列在结果里找不到就跳过绘图并给出 `warning` 提示（否则前端只会画出全 0 的图，比不出图更容易误导）。

**现状**


真正生效的聚合是模型写在 SQL 里的 `GROUP BY`（`SYSTEM_TEMPLATE:46` 明确要求「SQL 使用 GROUP BY 聚合查询」）。也就是说，AI 链路的 `aggregation` 只是**记录性元数据**；而手动建图表时，用户在「聚合方式」下拉里选了「求和 / 计数 / 平均」，**渲染结果不会发生任何变化**。

**影响**

- **手动建图表页**：下拉是误导性 UI —— 用户以为选了「求和」就会聚合，实际无效果，容易误判为「系统算错了」；

- 两种解读对应两种不同的修复方向，**需先确认产品意图**。

**建议方案（二选一，取决于产品意图）**

1. **若聚合应由 SQL 负责（与当前实现一致）**：把手动建图表页的「聚合方式」下拉**移除**，或改为只读展示并标注「聚合请写在 SQL 里」；AI 链路可保留该字段仅作审计留痕。
2. **若希望前端支持聚合**：在 `ChartCard.vue` 的数据装配处（`seriesValues()`，`:114-119`）按 `aggregation` 先做 `sum / count / avg / max / min` 聚合再渲染，并补前端测试。

无论选哪个，都建议顺手在 `AGGREGATIONS`（`:203`）旁补一行注释说明该字段的实际作用，避免后续维护者重复困惑。

**验证方式**

**状态**：✅ 已修复（2026-10-20）

**修复说明**：选建议方案 2（**让前端真正支持聚合**），而不是删掉那个下拉 —— 删 UI 会让「按类目汇总」这个合理需求无处安放，而实现成本只有十几行：

# 八、交互体验

## H1 智能查询发送后无法停止

**级别**：P1

**现象**：在「智能查询」里发出问题后，发送按钮变成 loading 且输入框被禁用，**没有任何中断入口**。模型思考慢、或工具循环跑偏时，用户只能刷新页面干等；即便关掉页面，后端也感知不到，仍在消耗 token。

**根因**：前端 `stores/agent.ts` 的 `fetch("/api/agent/chat")` **没有传 `signal`**，也没有 `AbortController` —— 连接一旦建立就只能等服务端发完。后端本身没有问题：Starlette 的 `StreamingResponse` 在收到 `http.disconnect` 时会取消任务，只是从来没有人去断开它。

**修复**

| 位置 | 改动 |
|---|---|
| `stores/agent.ts` | 新增模块级 `activeAbort` + `stop()`；`sendMessage` 传 `signal`；`AbortError` 不再当失败，而是标记 `stopped` 并保留已产出内容 |
| `stores/agent.ts` | 切换 / 删除会话前先 `stop()`，避免流式事件写进已被替换的消息列表；`streaming` 期间拒绝重复发送 |
| `SmartQueryView.vue` | 生成中把「发送」换成「停止生成」；消息尾部渲染「已停止」小标签 |
| `routers/agent.py` | SSE 响应补 `Cache-Control: no-cache` + `X-Accel-Buffering: no`（防代理缓冲导致断开感知延迟）；取消时记一条 info 日志 |

**验证**：起了一个最小 uvicorn 服务挂载 `sse()`，用原始 socket 模拟浏览器 abort（直接关 TCP）—— 计数冻结在 4 不再增长，生成器收到 `CancelledError`，响应头含 `x-accel-buffering: no`。另加 `tests/test_agent_sse.py` 两条用例锁住响应头与取消传播。

**已知限制**

- 已执行的 SQL 无法回滚（`asyncio.to_thread` 里的同步驱动查询杀不掉，会跑完并释放连接）；
- 停止后**不落库**：本轮问答不会写进会话历史（用户消息已存，助手回复没有）。刷新后只看到问题、没有答案。

**状态**：✅ 已修复（2026-10-23）
