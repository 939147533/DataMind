## 第 4 页 · 痛点分析（约 65 秒）

**【本页要点】** 三类角色，各三条痛点，共九条。

**【口播稿】**

我们先看现状。在银行、运维、业务分析这些场景里，取数和用数普遍存在三类问题，对应三类角色。

**第一类是业务人员。** 取数要提申请、等排期，链路长、周期久；好不容易拿到数据，只有数字没有图，做趋势还得自己导到 Excel 里画；想随时看一眼数据，却没有自助入口，处处要依赖技术同事。

**第二类是开发人员。** 复杂的 SQL 不够熟练，常用的查询反复重写；想让大模型帮忙写 SQL，可它并不了解真实的表结构，生成的语句不能直接用；更麻烦的是，一旦误执行了 DML 或者 DDL，就会造成数据事故。

**第三类是运维和 DBA。** 负责的系统多，很难熟悉所有的库表结构；各个数据库的语法和客户端都不统一，运维很繁琐；而且缺少一个统一的可观测视图 —— 谁查了什么、哪里慢，看不清楚。

## 第 5 页 · 解决方案（约 30 秒）

**【本页要点】** 一句话方案：Agent 驱动的工作台，五个能力组成闭环。

**【口播稿】**

针对这些痛点，我们的方案是：**构建一个由 AI Agent 驱动的数据库查询与运维工作台。**

它把 **自然语言查询、SQL 工作台、可视化报表、权限管理、运维监控** 这五件事，整合成一个闭环。

这样一来，不会写 SQL 的业务人员可以安全地查数，会写 SQL 的技术人员效率更高 —— 这正是我们一开始说的那两句话。

## 第 16 页 · AI Agent 深度集成（约 70 秒）

**【本页要点】** 不是"调个模型"，而是工程闭环：工具调用 / 失败自愈 / 经验复用 / 流式透明。

**【口播稿】**

先说 AI Agent。我们想强调的是：**它不是简单地调用大模型，而是把「工具调用、失败自愈、经验复用」做成了一个工程闭环。**

**第一，工具调用。** Agent 会按需调用四个工具 —— 查表清单、查列信息、采样数据、看执行计划，实时拿到真实的表结构和数据，从源头上杜绝编造表名列名。

**第二，失败自动修正。** 只读查询执行失败时，我们把真实的报错回传给大模型，让它自动修正并重试；但如果是鉴权失败这类非 SQL 错误，就不重试，避免无效循环。

**第三，历史 SQL 复用。** 每一轮对话都会注入历史上执行成功的 SQL 作为示例，按提问相似度、表名重合度和执行频次加权排序，取最相关的前 3 条。

**第四，多轮会话加流式透明。** 上下文是连续的，可以追问、可以改条件；SSE 把 thought、tool、sql、result 逐段推给前端，过程完全透明。

## 第 17 页 · SQL 分级鉴权（约 55 秒）

**【本页要点】** 四行表格：READ 自动、DML 确认、DDL 高危、混合逐条。

**【口播稿】**

再讲 SQL 分级鉴权，这是整个系统安全的底座。我们用一张表来说明。

**只读类**，包括 SELECT、SHOW、DESC、EXPLAIN，**自动执行**，直接返回结果。
**写数据类**，INSERT、UPDATE、DELETE，需要**手动确认**，确认前会返回影响行数预览和一个 execution_id。
**改结构类**，CREATE、ALTER、DROP、TRUNCATE，属于**高危确认**，会红色警告并展示完整的 DDL。
**多条混合的 SQL**，则**逐条确认**，按类型分别处理。

有两条硬约束：所有 SQL 必须强制走服务层，不允许绕过鉴权直接调用适配器；确认的时候会再鉴权一次，并写入审计。

审计与监控，解决的是两个视角的问题：**可追溯**和**可观察**。

## 第 19 页 · 工程化与安全（约 45 秒；质量保障用展开版则约 90 秒）

**【本页要点】** 三根柱子：安全围栏 / 工程规范 / 质量保障。

**【口播稿】**

最后是工程化与安全，我们把它归成三根柱子。

**安全围栏**：数据库密码、SSH 私钥、AI Key 都用 Fernet 加密；对外只暴露 `has_*` 这样的布尔值，绝不回传明文；用户密码用 pbkdf2 哈希，会话走 24 小时的 Cookie。

**工程规范**：统一响应结构 `code / message / data`；统一的异常处理和请求校验；数据文件都用相对 `data/` 目录的路径，迁移时不用改配置。

**质量保障**（展开版，约 60 秒）：这块我们做得比较实，不是只写了几个用例，而是按层次把关键路径都覆盖了。后端有 **167 个自动化用例**，分布在 28 个测试文件里，覆盖用户与角色、连接池、SQL 执行与分级鉴权、AI Agent、元数据管理、导出、监控和大模型连通性；前端有 **19 条端到端断言**，用真实浏览器把登录、选数据源、执行查询、写操作确认、结果导出、审计留痕这一整条链路跑一遍，任何一环断了都会失败；另外还整理了一份 **19 个案例的 AI 查询验收清单**，从基础查询覆盖到多表关联和风控场景，逐条核对生成的 SQL 与期望结果。代码层面还配了 ruff 静态检查和前端类型检查，提交前必须通过。所以这个系统不是「功能做完就交付」，而是每一条关键路径都有测试兜底。

> **时间不够时的简版（约 25 秒）**：后端 167 个自动化用例覆盖了用户角色、连接池、SQL 鉴权、Agent 和导出等关键路径；前端 19 条端到端断言用真实浏览器跑通整条链路；另有 19 个 AI 查询验收案例逐条核对。关键路径都有测试兜底。

**Q1：大模型生成的 SQL 会不会不安全？**
不会。所有 SQL 都强制走服务层，执行前先做风险分类 —— READ 自动执行，DML 和 DDL 必须人工确认；确认时再次鉴权，并写入审计。模型无法绕过这道门。

**Q2：和直接用大模型聊天写 SQL 相比，区别在哪？**
三点：一是 Agent 会主动调用工具读取真实表结构、采样数据和执行计划，不会编造表名列名；二是失败后会把真实报错回传自动修正重试；三是会复用历史执行成功的 SQL 作为示例，越用越准。

**Q3：业务人员不懂 SQL，怎么保证他查到的数据是对的？**
他拿到的不只是数字，还有 Agent 的完整思考过程、生成并执行的 SQL 原文，以及结果的可视化图表。SQL 全程可见、可审计，可以随时复核。

**Q4：支持哪些数据库？扩展新库要多久？**
目前已支持 SQLite、MySQL、PostgreSQL、Oracle、MongoDB、OceanBase、GoldenDB 七类，都通过统一适配层屏蔽方言差异。新增数据源只需实现适配器接口并注册，即可在连接管理中直接使用。

**Q5：这个系统现在能上线吗？测试做到什么程度？**
可以。后端有 167 个自动化用例，前端有 19 个端到端断言，另有 19 个 AI 查询验收案例；部署上是 Docker 多阶段构建、单端口交付，也支持本地前后端分离开发。
