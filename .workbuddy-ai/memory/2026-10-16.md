## DataMind 方言切换机制调研（问答）

问题：会话中切换数据源后，系统如何自动切换到对应数据库方言？

**结论：没有"切换"动作，方言是每次请求按当前数据源即时装配的。**

调用链：
1. 前端 `SmartQueryView.vue:191` → `send()` 把当前 `dsId` 传给 `agent.sendMessage()`
2. `stores/agent.ts:101` → POST `/api/agent/chat` 请求体带 `datasource_id`
3. `routers/agent.py:58` → `agent_service.agent_chat(...)`
4. `agent_service.py:318-322` → 用请求的 `datasource_id`（缺省回退 `session.datasource_id`）查 DataSource
5. `agent_service.py:146-160` `_schema_info(ds)` → `build_adapter_async(ds)` → 读适配器**类属性** `db_type` / `dialect_hint`
6. `agent_service.py:350-355` → 填入 `SYSTEM_TEMPLATE` 的 `{db_type}` / `{dialect_hint}` 占位符（模板定义在 `agent_service.py:23-25`）

`dialect_hint` 定义位置（类属性，每个库一份）：
- `mysql_adapter.py:15` MySQL：DATE_FORMAT / DATE_SUB(NOW(), INTERVAL N DAY) / LIMIT / 反引号
- `postgres_adapter.py:16` PostgreSQL：TO_CHAR / DATE_TRUNC / CURRENT_DATE - INTERVAL 'N days' / LIMIT
- `oracle_adapter.py:15` Oracle：TO_CHAR/TRUNC / TRUNC(SYSDATE)-N / FETCH FIRST N ROWS ONLY（不支持 LIMIT）
- `sqlite_adapter.py:11` SQLite：strftime / date('now','-N day') / LIMIT
- `base.py:73` 基类默认 `""`；**MongoDBAdapter 未定义，继承空串**

配套的方言隔离：
- Schema 摘要 `schema_summary()` 也走当前 ds 的适配器
- few-shot 按 datasource 隔离：`sql_examples.py:187` `where QueryHistory.datasource_id == ds_id`，缓存 `_cache: dict[int, ...]` 按 ds_id 分桶

## DataMind 权限控制机制调研（问答）

**模型**：`User.role` 是 `String(20)`，存的是**角色 code 字符串，不是外键**（`models.py:43`）。`Role.permissions` 是 Text 存 JSON 数组（`models.py:191`）。`Role.is_builtin` 标记内置角色。

**14 个权限码**（`permissions.py:13-28`），按 4 组分类：工作台（workspace / ai_query / sql_write / sql_ddl / agent）、连接（connections / connections_manage）、报表（reports / reports_manage）、系统（settings / audit / users / roles / monitor）。

**5 个内置角色**（`permissions.py:32-63`）：admin（`["*"]`）、tech_manager、tech_query、biz_manager、biz_query。`admin` 是特例 —— `get_user_permissions` 直接返回 `{"*"}`，**不查 roles 表**（`permissions.py:70-71`）。种子逻辑在 `seed.py:140-152`。

**三道关卡**：
1. 登录态 `get_current_user`（`deps.py:15-29`）：Cookie `session_token` → 查 sessions 表 → 校验 `expires_at` → 校验 `user.is_active`
2. 路由级 `require_permission` / `require_any_permission`（`permissions.py:89-102`）：作为 FastAPI 依赖挂在路由上
3. SQL 操作级 `check_sql_permission`（`permissions.py:112-121`）：**不在路由上，在 `execute_sql` 内部**（`sql_service.py:518`），按 `classify_statement` 的结果动态判定 —— READ → workspace|ai_query；DML → sql_write；DDL → sql_ddl

**关键设计**：SQL 权限必须放服务层，因为同一条路由 `/api/sql/execute` 既能跑 SELECT 也能跑 DROP TABLE，权限取决于**语句内容**而非路由。

**写操作收口点核实**（全部经 `execute_sql`）：
- `routers/sql.py:20`、`routers/metadata.py:116`（alter_table）
- `services/metadata_service.py:172/180/188`（update/insert/delete_table_row）
- `services/agent_service.py:422`（READ）、`agent_service.py:518`（确认后执行）
- 唯一旁路 `services/export_service.py:40` 直调 `adapter.execute`，但前面有硬性 READ 校验（`export_service.py:35-36`）

**元数据路由的宽松守卫是有意设计**：`metadata.py` 的 alter_table / update_table_row 等只要 `workspace|reports` 就能进，真正的 DML/DDL 权限在 `execute_sql` 里收口。属"路由宽松 + 服务层严格"的分层。

**二次鉴权（TOCTOU 保护）**：`confirm_execution` 在执行前**再查一次权限**（`sql_service.py:569`），防止确认期间权限被降级。

**鉴权被拒也审计**：`execute_sql` 捕获 HTTPException 后写 `status="denied"`（`sql_service.py:519-523`）。

**前端**：`router/index.ts:36-55` 用 `meta.permission` / `meta.permissionAny` 做守卫；`stores/auth.ts:32-40` 的 `hasPermission` 判断 `perms.includes("*")`；`defaultHome()` 按权限顺序找落地页。前端只做体验，非安全边界。

**内置角色保护**：code/name 不可改（`roles.py:138-142`）、不可删（`roles.py:170-171`）、只有 admin 能有 `*`（`roles.py:134-135`）、权限码必须存在于 `PERMISSION_NAMES`（`roles.py:37-42`）、角色下有用户不能删（`roles.py:172-174`）。

**用户自锁保护**（`users.py`）：不能禁用自己（150-151）、不能删自己（177-178）、不能禁用/删除/降级最后一个启用的 admin（152-154、157-159、179-180）。

## 新发现的潜在风险（建议加入优化清单）

1. **`check_sql_permission` 的 fail-open 分支**（`permissions.py:113-114`）：
   ```python
   if not user_id:
       return
   ```
   `user_id` 为 None/0 时**直接放行、不做任何鉴权**。已核实当前所有调用点都传了 `user.id`，所以不可达；但这是"默认放行"写法，将来新增调用点若漏传 `user_id` 会静默绕过鉴权。建议改为 fail-closed（抛 401）。
2. **`User.role` 是裸字符串非外键**：删角色虽检查了"角色下还有用户"，但若出现悬空角色码，`get_user_permissions` 返回空集合（`permissions.py:73-74`）→ 静默降级为无任何权限。属 fail-closed，安全但排查困难。
3. **权限每次请求实时查库**（`get_user_permissions` 查 roles 表），无缓存 —— 改权限立即生效，代价是每请求多一次查询。

## Fernet 加密调研（问答）+ 新增清单项 D2

`backend/app/security.py` 用 Fernet（AES-128-CBC + HMAC-SHA256，encrypt-then-MAC）加密**可逆**机密：数据源密码、SSH 私钥、大模型 API Key；用户登录密码走 `pbkdf2_sha256` 单向哈希。密钥三级回退：`DBAGENT_SECRET_KEY` 环境变量 → `DBAGENT_SECRET_KEY_FILE` → `data/secret.key`（自动生成 chmod 600）；`warm_up()` 启动预加载，`_warn_if_key_permissive()` 检查权限。`_fernet` 是模块级单例 → 换密钥必须重启进程。

**已补入 `docs/优化清单.md` 编号 D2（P2）**：`decrypt_text`（`security.py:73-79`）`except Exception: return ""`，把「解密失败」伪装成「空值」。4 个调用点：`sql_service.py:295`（数据源密码）、`:302`（SSH 私钥）、`llm_providers.py:22`（API Key）、`system.py:55`（测试连接）。后果是密钥问题被报成凭据问题（「Access denied」/「Key 无效」）。

**已核实排除**：不存在「解密失败 → 空值回写覆盖」的数据丢失路径 —— `connection_service.py:99-102` 有 `if data.password:` 守卫，`system.py:120-124` 仅在 `payload["api_key"]` 非空时才重新加密并 pop 掉该字段。所以 D2 只影响可诊断性，不影响数据安全。

## 图表类型自动选择的实现（核实结论）

- 链路：`agent_service.SYSTEM_TEMPLATE:40/46` 给模型约定 chart 格式（type 限 bar|line|pie）→ 模型在**最终 JSON** 里输出 `chart` → `_parse_chart:206-232` 白名单校验（type/x_column/y_columns 非空，aggregation 白名单否则回落 none）→ `:468` 仅在 `op_type == "READ"` 分支解析 → `:470` 发 SSE `chart` 事件 → 前端 `SmartQueryView:162-176` 转 Chart，`ChartCard.vue` 渲染。
- **无规则引擎/启发式推断**：选型完全由 LLM 决定；且 `chart` 取自 `parsed`（SQL 执行前生成的那份 JSON），模型**看不到结果行**，所谓「数据特征」实为 Schema 摘要 + 方言 + few-shot + 用户意图 + 自己写的 GROUP BY 结构。
- 前端 `ChartCard.vue` 支持 11 种（bar/line/area/pie/scatter/radar/funnel/gauge/kpi/rank/progress，见 `ReportsView.vue:203-215`），AI 链路只会传前 3 种，`SmartQueryView:170` 兜底 `|| "bar"`。
- **两处待记入清单的发现**：① `aggregation` 字段从模型→后端→库→前端一路传递，但 `ChartCard.vue` **从不读取**（grep 零匹配），对 AI 生成的图表是装饰性字段，真正生效的是模型 SQL 里的 GROUP BY；② SQL 自动修正时 `:440 parsed = _extract_json(raw)` 会覆盖 parsed，修正后 JSON 若未带 `chart`，图表丢失（`:468` 读的是覆盖后的 parsed）。
- 演讲稿 `docs/DataMind数据库Agent项目介绍-演讲稿.md:159`「系统会根据数据的特征自动选择合适的图表类型」口径偏强，建议改为「由大模型结合表结构与提问意图自动选择图表类型（柱状/折线/饼图），系统做白名单校验」。

## LLM Provider 三方法接口核实（chat / stream / ping）

- 抽象定义 `llm_providers.py:13-39`：`chat(messages, json_mode=False) -> str`、`stream(messages) -> AsyncIterator[str]`、`ping() -> dict` 三个 `@abstractmethod`；`validate()`（`:24-29`）是**非抽象**方法（有默认实现），缺 Key/地址时快速失败。
- **7 个调用点全部只用这三个方法**：chat → `agent_service.py:180`（首轮+工具轮 JSON）、`:439`（SQL 修正重试）、`routers/metadata.py:107`（生成 DDL）；stream → `agent_service.py:485`（结果总结）、`:554`（SQL 解释）、`:577`（SQL 优化）；ping → `routers/system.py:77`。业务层无一处出现 openai/anthropic SDK 字样。
- 差异吸收点：`ClaudeProvider._split()`（`:103-106`）把 system 从 messages 抽出来单独传参（Anthropic SDK 不允许 system 在 messages 里）；`json_mode` 在 Claude 侧**被忽略**；流式 OpenAI 用 `chunk.choices[0].delta.content`、Claude 用 `stream.text_stream`。
- **json_mode 失效的兜底链**（重要）：Claude 下 JSON 只靠提示词约束 → `_extract_json()`（`agent_service.py:163-172`）剥 ``` 围栏并截取首个 `{` 到末个 `}` → `_chat_json_with_retry()`（`:175-186`）重试 3 次、每次间隔 1s。接新网关时这一项最值得先测。
- **新发现（未记入清单，待用户决定）**：`ClaudeProvider._client()`（`:98-101`）**没有传 `base_url`**，而 `OpenAICompatProvider._client()`（`:45-48`）传了 `base_url=self.config.api_base or None`。即 `AIConfig.api_base`（`models.py:53`）在 `provider=claude` 时**填了不生效也不报错**，无法接 Anthropic 代理/中转。与 D2（`decrypt_text` 静默吞异常）同属「配置项静默失效」类问题。
- 另注：`agent_service.py:339` 与 `system.py:69` 用 `getattr(provider, "validate", None)` 做防御性调用，但 `validate` 是基类具体方法、必然存在，该 `getattr` 属多余。
